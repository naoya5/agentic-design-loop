# アーキテクチャ

## 設計思想

本プロジェクトは GAN（敵対的生成ネットワーク）のアプローチをマルチエージェントシステムに応用したもの。

核となる考え方：**作成するエージェントと評価するエージェントを完全に分離する**。

エージェントは自分の作品を過大評価する傾向がある。特にデザインのように「成功か失敗か」を決定的に判断できないタスクでは、ソフトウェアテストのような客観的チェックが存在しないため、この問題が顕著になる。Generator と Evaluator を分離することで、この自己評価バイアスを解消する。

## 全体構成

```
┌─────────────────────────────────────────────────────┐
│                 Orchestrator (TypeScript)            │
│                                                     │
│  ループ制御 / ファイルI/O / コスト管理 / 判定ロジック │
│                                                     │
│  ┌───────────┐    file://    ┌───────────────┐      │
│  │ Generator │ ──────────→  │   Evaluator   │      │
│  │  Agent    │  index.html  │    Agent      │      │
│  │           │              │               │      │
│  │ systemP:  │  evaluation  │ systemP:      │      │
│  │ デザイン   │ ←────────── │ 4基準採点     │      │
│  │ ガイド    │   .json      │ Chrome MCP    │      │
│  └───────────┘              └───────────────┘      │
└─────────────────────────────────────────────────────┘
```

## なぜオーケストレーターはエージェントではないのか

オーケストレーターを普通のTypeScriptコード（`query()` を順番に呼ぶプログラム）として実装する理由：

1. **ループ制御の明示性**: `for` ループでイテレーション数を管理。エージェントに委ねると暴走リスクがある
2. **ファイルI/Oの確実性**: `existsSync` / `readFileSync` で生成物の存在を確認し、JSON parse の失敗もハンドリングできる
3. **コスト管理**: 各 `runAgent()` 呼び出しのコストを累積して追跡
4. **判定ロジックの分離**: 合否判定をオーケストレーターに持たせることで、Evaluator の採点と判定を分離

## エージェント間通信：ファイルベース

エージェント間の通信はすべて `output/` ディレクトリ内のファイルで行う。

```
output/
├── iteration-1/
│   ├── index.html          ← Generator が書き出し
│   └── evaluation.json     ← Evaluator が書き出し
├── iteration-2/
│   ├── index.html          ← Generator が前回HTMLを読み＋改善
│   └── evaluation.json
└── ...
```

### なぜファイルベースか

- **透明性**: 各イテレーションの成果物が残り、人間が確認できる
- **デバッグ容易性**: 途中で止まっても、最後に成功したイテレーションのHTMLは残る
- **再現性**: evaluation.json のスコア推移を追跡できる
- **エージェント間の疎結合**: 各エージェントはファイルパスだけ知っていればよい

## スクリーンショット → 評価のフロー

```
Evaluator Agent
│
├─ 1. mcp__chrome-devtools__navigate_page
│     file:///path/to/output/iteration-N/index.html を開く
│
├─ 2. mcp__chrome-devtools__take_screenshot
│     スクリーンショットがインラインで Claude に表示される
│     （Claude のマルチモーダル能力で視覚分析）
│
├─ 3. 4基準で採点
│     スクリーンショットを見ながら各基準 1-10 でスコアリング
│
└─ 4. Write で evaluation.json を書き出し
```

重要なポイント：`take_screenshot` の戻り値は画像がインラインで会話に含まれるため、Claude が直接「見て」分析できる。ファイルに保存して再読み込みする必要はない。

## コンテキスト不安への対策

記事で指摘されている「コンテキスト不安」問題への対策：

1. **各エージェント呼び出しは独立したコンテキスト**: `query()` の各呼び出しは新しいコンテキストで開始される
2. **必要な情報だけをプロンプトに含める**: 前回の evaluation.json の内容をテキストとして渡す（コンテキスト全体を引き継がない）
3. **`maxTurns` によるサーキットブレーカー**: Generator は 25 ターン、Evaluator は 10 ターンで強制終了
4. **構造化されたハンドオフ**: 前エージェントの出力（JSON）を次エージェントのプロンプトに明示的に埋め込む

```
┌─────────────────────────────────────────────────────────┐

│                                                         │
│  ┌──────────┐                                           │

│  │ Agent    │      (1回のみ実行)                        │
│  └──────────┘                                           │
│       │                                                 │
│       ↓ sprints[]                                       │
│  ┌─────────────────────────────────────────────┐        │
│  │  for each sprint:                           │        │
│  │                                             │        │
│  │  ┌───────────┐         ┌───────────────┐    │        │
│  │  │ Generator │ ──app── │ QA Evaluator  │    │        │
│  │  │  Agent    │         │    Agent      │    │        │
│  │  │           │  eval   │               │    │        │
│  │  │ コード実装 │ ←────── │ ブラウザテスト │    │        │

│  │       ↑                      │              │        │
│  │       └── retry (max 3) ─────┘              │        │
│  └─────────────────────────────────────────────┘        │
└─────────────────────────────────────────────────────────┘
```

### Planner の設計原則

> 最初は大まかに設定する。プランナーが事前に細かい詳細を指定しようとするとエラーが発生しやすく、仕様書のエラーが下流の実装に連鎖的に影響を及ぼす。

- 製品のコンテキストと高レベルの技術設計に焦点
- 詳細な技術実装は指定しない
- スプリント分割: 3-5個、各スプリント1機能

### Generator のスプリント戦略

- 一度に一つの機能を追加
- 各スプリントの最後に自己評価を実施
- git でバージョン管理（スプリントごとにコミット）

### QA Evaluator のテスト方法

- Chrome DevTools MCP で実際にアプリを操作
  - `navigate_page` でアクセス
  - `click`, `fill`, `press_key` でユーザー操作を再現
  - `list_console_messages` でエラーチェック
  - `take_screenshot` で視覚確認
- コードも直接 Read で読んで品質評価
